# sarvam-meter-plasmoid — adversarial code review

Reviewer: adversarial pass against `SPEC.md` v1 (shared contract) over the snapshot in
`repo-snapshot.zip` (repo root at zip root). Baseline: `python3 -m unittest discover -s tests`
→ **334 tests, OK** (18.3 s, CPython 3.12.13, Linux).

Scope of this pass: interface drift between modules, cost arithmetic, ledger concurrency and
corruption, proxy streaming/SSE/multipart/oversize edges, daemon robustness and secret leakage,
CLI signals and exit codes, SSRF/log-secret security, static QML. Everything below was found by
running code; every finding names the exact input and the observed output. One item (MN-10) is
explicitly **unconfirmed** because it needs a Qt/Plasma runtime.

**Findings: 1 critical, 6 major, 11 minor, 8 nit (26 total).**

the repo tree); each cell gives a self-contained command that reproduces the finding, plus the

## Verified correct

Checked by hand or by running code; these are genuinely fine, so the maintainer can skip them.

**Cost arithmetic (`rates.py`)**
- Chat pricing separates the three buckets and never double-counts cached tokens. Hand check:
  `cost_for("chat","sarvam-105b", 600_000, "tokens", cached_quantity=400_000, out_quantity=100_000)`
  → `17.0` = `(600k×15 + 400k×5 + 100k×60)/1e6`. The proxy passes `in−cached`, `cached`, `out`
  (`proxy.py:376-380`) and clamps `cached = min(cached, in)`, so a lying `prompt_tokens_details`
  cannot make the cached bucket exceed the prompt.
- Legacy blended path (no `out_quantity`): `cost_for("chat", …, 1e6, cached=4e5)` → `11.0` = `(600k×15 + 400k×5)/1e6` — correct, and documented as understating output by up to 4×.
- STT is per second of a per-minute rate: `cost_for("stt", None, 30, "seconds")` → `0.245` (`30/60×0.49`); `0 s` → `0.0`.
- TTS is per 1000 characters: `1000 chars` → `3.0`; `1234 chars` → `3.702`.
- Unpublished rates (`translate`, `transliterate`, `lid`) → `0.0` and `rate_known()` `False`; unknown api/model → `0.0`/`False`; model lookup is exact-then-`default`.
- Rounding is consistent: 6 dp on write (`record_event`, `cost_for`), 2 dp money / 4 dp fractions in the payload.
- `0` quantity → `0.0`; `nan`/`inf` quantity → `ValueError` ("quantity must be finite"); `bool` rejected as a number.

**Ledger (`ledger.py`)**
- Load test: 8 threads × 200 events plus 4 concurrent reader threads doing `spend_since`/`calls_since`/`spend_by_api_since`/`count_status_since` → **1600 rows inserted, 1600 distinct ids returned, 0 write errors, 0 read errors, 0 "database is locked"**, journal mode `wal`.
- Two `Ledger` instances on the same file see each other's rows immediately (1601 after the second instance writes).
- Boundary semantics are consistent and defensible: `spend_since` is inclusive (`ts >= ?`) and `purge_before` is exclusive (`ts < ?`), so an event exactly at the boundary is counted and never purged — verified with three events around `2026-01-01T00:00:00Z`.
- Corrupt DB file → `sqlite3.DatabaseError("file is not a database")` at construction (the daemon catches it and serves degraded); read-only DB → reads work, writes raise `OperationalError` (the proxy's recorder catches and logs).
- `meta` is serialised with `sort_keys=True, ensure_ascii=False`; `set_balance` upserts row 1; `get_balance()` returns `None` when unset.
- `local_day_start_iso`/`local_month_start_iso` bucket in the *local* calendar: `2026-11-01 00:30 IST` → `2026-10-31T18:30:00Z` for both day and month start.
- 960-event load through the daemon: 60 concurrent `/v1/status` calls, **zero** `errors` entries, `calls.today` monotonically non-decreasing, final `spend.today` exactly `0.1` for 960 × 0.0001.

**Proxy (`proxy.py`)**
- Chat JSON: `prompt=1000, cached=400, completion=500` → `quantity=1500, cost=0.041, estimated=0` — matches the hand calculation.
- SSE: a `usage` chunk deliberately split across two upstream writes (and two TCP segments) is still parsed (`quantity=1200, cost=0.0315`); `[DONE]` is ignored; the relayed stream is well-formed chunked output.
- A response with no top-level `usage` but a *quoted* usage example inside the model's own content does **not** produce phantom usage (`chat_usage` → `None`, row `quantity=None, cost=0.0, estimated=1`) — the `\"` escaping defeats the text-scanning fallback. Same for `chat_stream_usage`.
- 200 with an empty body → `estimated=1, quantity=None, cost=0.0`; `usage` with `prompt_tokens` only → priced as input (`700 → 0.0105`), no crash.
- Every upstream status is recorded exactly once, with `status` set and cost 0 for errors: 200/400/402/429/500/501/503 all produced one row; `402` additionally sets `kv["quota_exhausted_at"]`.
- Upstream unreachable → `502` with `{"error":{"message":"upstream unreachable","code":"meter_upstream_error"}}` and **no** ledger row.
- Path safety: `/../etc/passwd`, `http://evil/v1/chat/completions`, `v1/chat` (no leading slash) → `400 meter_bad_path`; `HEAD`/`OPTIONS`/`PUT` → `405` (per SPEC §8.9).
- Oversize: declared `Content-Length > max_body_bytes` → `413` before anything is forwarded (upstream saw the previous request, not this one) and no row; chunked body exceeding the limit mid-stream → `413` with the JSON envelope, upstream received only the first ≤limit bytes, no row.
- Query strings are forwarded upstream intact (`/v1/chat/completions?api_key=QUERYSECRET`) but stripped from `meta.path` and from the log line — `QUERYSECRET` appears in neither.
- `api-subscription-key` and `Authorization` never reach the log, `meta`, or the ledger (asserted by substring search over the captured log and the whole `events` table).
- multipart STT with the audio part **not** first → exact duration (9.5 s) because the container signature is located anywhere in the head; TTS counts code points, not bytes (`"a"+10 emoji` → 11 chars, 0.033).
- Request bodies are streamed in 64 KiB chunks; a POST with neither `Content-Length` nor `Transfer-Encoding` is forwarded as `Content-Length: 0` and handled.

**Daemon (`daemon.py`)**
- Routes and shapes: `/v1/status` `200` + `application/json; charset=utf-8` + `Cache-Control: no-store`; `/v1/health` `{"ok":true,"version":"0.1.0","uptime_seconds":N}`; `/v1/refresh` `POST` only; `/v1/config` redacted; unknown path → `404` JSON; wrong method → `405` JSON; `/v1/status?x=1` and `//v1/status` both resolve.
- `/v1/config` with `management_key = "SUPERSECRETKEY"` → `"management_key": "***"` and the literal never appears in `/v1/config` or `/v1/status`.
- A 3 s-per-call CLIProxyAPI stand-in: `/v1/status` answered in **0.010 s** while `/v1/refresh` was still in flight (6.27 s) — no blocking, no deadlock; after the refresh the snapshot is `reachable: true`.
- `shutdown()` during an in-flight refresh returns in **0.20 s** and the port is released (`ConnectionRefusedError` afterwards).
- A second daemon on the same port raises `OSError: [Errno 98] Address already in use`.
- A 200 KB header → `431`; a 100 KB request line → `414`; the daemon keeps serving (`200` afterwards).
- Unopenable `db_path` (`/proc/definitely/not/writable/x.db`) → daemon starts, `/v1/status` returns `200` with `errors:[{"source":"ledger","code":"read_failed",…}]` and zeroed numbers (SPEC edge case 5).

**CLI (`cli.py`)**
- Exit codes match the contract: no command `2`, `--help` `0`, unknown subcommand `2`, missing `--unit` `2`, missing config `2`, invalid JSON `2` (message names the file and the reason, never the contents), `--quantity nan` `2`, `balance set -5` `2`, port already in use `1` with `cannot bind daemon on 127.0.0.1:18787: [Errno 98]`, `status`/`doctor` `0`.
- `init` writes mode `0600` inside a `0700` directory, and the document is byte-for-byte equal (as parsed JSON) to `packaging/config.example.json`.
- `SIGINT` on `serve` exits `0` and the DB is checkpointed.
- `status --json` emits valid JSON; human `status` prints one line per source plus error lines on stderr.

**Security**
- SSRF guard on `cliproxy.base_url`: accepts `127.0.0.1`, `127.5.5.5`, `localhost`, `[::1]`, `[::ffff:127.0.0.1]`; rejects `example.com`, `10.3.40.219`, `169.254.169.254`, `0.0.0.0` unless `allow_remote: true`; the userinfo trick `http://127.0.0.1@example.com` is correctly judged on `example.com` and rejected. `CliproxyClient.__init__` re-checks independently.
- Redirects are not followed: a `302` pointing at `/v8/management/usage-queue` produced `code:"http_error"` and the server saw **no** follow-up request.
- The destructive usage-queue endpoints are refused before the transport is reached (`code:"forbidden_endpoint"`, no request observed).

**QML statics (read, not rendered — no Qt installed)**
- All five `Plasmoid.configuration.<key>` reads (`daemonUrl`, `refreshSeconds`, `compactMode`, `warnBelowPercent`, `showApiBreakdown`) have a matching `main.xml` entry with the documented default (`http://127.0.0.1:8787`, `60`, `sarvam`, `20`, `true`), and `configGeneral.qml` declares exactly the five matching `cfg_*` properties.
- Every payload key the QML reads exists in `build_status`'s output: `sarvam.{configured,currency,balance.{known,remaining,starting,spent_total},spend.{today,month},calls.today,by_api,quota_exhausted}`, `cliproxy.{configured,reachable,worst_fraction,accounts[].{name,label,provider,plan,status,error,buckets[].{window,remaining_fraction,description,reset_at}}}`, plus `generated_at`, `stale`, `errors`, `schema`. (The payload's `rate_limits` and `untracked_calls` are emitted but unread — not a defect.) `configGeneral.qml` reads `payload.version` from `/v1/health`, which does emit `version`.
- No unguarded `.length` on a possibly-null value: every list goes through `asArray()`/`textOf()`/`numberOr()`, `topApis`/`accountsList`/`errorList` fall back to `[]`, and `hasPayload`/`hasMeter` guard every `payload.*`/`meter.*` dereference.
- Delegate ids are declared before use (`apiRow.apiName`, `bucketBlock.unknown` → `fractionValue` → labels), and `unknown` is honoured (`remaining_fraction: null` renders the literal `unknown`, never `0%`).
- Root is `PlasmoidItem` with `compactRepresentation`/`fullRepresentation`; no `PlasmaCore.Units`, no `PlasmaComponents2`, no lowercase `plasmoid.*`, no `Item {}` root, no custom contextual actions, no `org.kde.plasma.core` gauge, no `QtQuick.Shapes`; `Bar.qml` is a plain `Rectangle` with `fraction`/`fillColor` and `Layout.fillWidth: true`; XHR is always asynchronous (`open(..., true)`); the timer doubles the interval on failure up to 10× and resets on success; `Component.onCompleted` refreshes immediately.

## Unconfirmed / what I could not reproduce

1. **MN-10** (QML handler ordering in `configGeneral.qml`) — needs a Plasma runtime; no Qt toolchain was installed, per the brief. Reported as a risk with the static reasoning only.
2. **"An allow-listed loopback name that resolves elsewhere."** The guard never resolves, so by construction `localhost` is trusted regardless of `/etc/hosts`/DNS. I could not demonstrate the malicious direction: `/etc/hosts` is root-owned and unmodifiable here, and there is no DNS on the loopback. The benign direction (a loopback-resolving name that is *rejected*) is proven in MN-3.
3. **`config.qml:31`** — `source: Qt.resolvedUrl("configGeneral.qml").toString().replace("file://","")` hands `ConfigCategory.source` an absolute filesystem path. Whether plasma-framework resolves that (the file's comment asserts it does) or treats it as a relative URL cannot be checked without plasma-framework; **not** counted as a finding.
4. **A truncation mid-body where the upstream declares `Content-Length: 500` and sends 27 bytes** — the proxy relays the declared length and closes; the client sees a truncated body (an `IncompleteRead` for `http.client`). This is faithful relay of a broken upstream, and the row is correctly `estimated=1, quantity=None, cost=0.0`, so I do **not** count it as a defect; noting it here because it looks alarming at first glance.
5. **Row visibility immediately after the response.** `_relay_response` flushes the body to the client *before* `record_from_exchange` runs, so a test that reads the response and then immediately queries the ledger can see zero rows. This is a measurement race in the test, not a defect (confirmed by adding a 0.4 s wait: the row appears). Worth knowing before writing new proxy tests.
